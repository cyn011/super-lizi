# 关卡设计文档 · 1-2「翠野·续章」

> 主交付文档（设计策略师 / 文策渊）。配套机器规格见 `1-2-content-spec.md`。
> 进度链：`1-1 翠野序章` → `1-2 翠野·续章`。本项目为原创「马里奥式」横版跳跃小游戏，IP 红线已遵守（无蘑菇/星/旗杆/水管工/龟壳；终点为**凯旋之门** `triumph_gate`）。
> 模式：验证关卡流水线复用 —— 仅使用已落地系统，零新实体类型。

---

## 1. 概念定位（Concept）

- **id**：`1-2`（同世界第二关）
- **命名建议**：**「翠野·续章」**（沿用 `1-1` 的「翠野」前缀，副标题「续章」点明同世界延续；如主理人想强化叙事梯度，备选「翠野·浅跃」强调本关新增的纵向跳跃与节拍节奏）。
- **theme**：`grass`（与 1-1 完全一致，验证调色板 / 资产 / 程序化生成器零改动复用）。
- **一句话概念**：栗宝在翠野继续前行，地形从 1-1 的平阔序章转为「更高、更密、更讲节奏」的续章 —— 同一片草地，却要踩着会呼吸的节拍平台与更密敌群过关。

## 2. 相对 1-1 的难度阶梯（Difficulty Ramp）

设计原则：**好玩的下一步，而非劝退**。所有提升均建立在「已落地机制的组合密度」上，不引入新规则。

| 维度 | 1-1 | 1-2 | 提升说明 |
|---|---|---|---|
| 关卡长度 | width 40（1280px） | **width 48（1536px，+20%）** | 展示流水线对可变宽度的兼容，也给更多呼吸与段落空间 |
| 敌人总数 | 4（各 1 种） | **8（4 种全覆盖，密度 ×2）** | 中段 + 后段 gauntlet 各叠一组；ci_li 出现 3 次、du_fu 2 次、chong_feng 2 次、shi_pao 2 次 |
| 节拍段 | 1 段，pattern `SSSSSSSSGGGGGGGG`（4s 实 / 4s 虚，宽松） | 1 段，pattern `GSGSGSGSGSGSGSGS`（**500ms 实 / 500ms 虚，更紧**） | 相位切换频率×8，验证「节拍相位可定制」且真正考验时机 |
| 检查点 | 1 个（仅 entity 内，checkpoints[] 为空） | **2 个**（mid + gauntlet 前） | 后段 gauntlet 密集，双检查点降低挫败、保留挑战 |
| 纵向玩法 | oneway 2 组 | oneway 2 组 + 悬浮 solid 1 组 + 节拍平台高位路线 | 鼓励「高位赏金路线」与「地面安全路线」双通道 |
| 种子 | 2 颗 | 2 颗（前段 1 + 后段 1） | 维持蜕变机制曝光；位置更靠关卡两端形成节奏锚点 |

**为何不劝退**：地面 `ty7-8` 全程连续（无落穴），失败代价低；节拍平台身处其下为实地，踩空也只是落回地面而非死亡；后段 gauntlet 虽密，但第二个检查点设在 gauntlet 末尾前，重来成本低。难度来自「更密的敌群 + 更紧的节拍 + 更长的路」，而非「一击即死的陷阱」。

## 3. 机制复用清单（验证流水线复用）

> 每一项均直接对应 1-1 已落地 schema，工程主程可「按 1-1 同款 loader/renderer 直接吃 JSON」。

| 复用系统 | 1-2 中的用途 | 验证点 |
|---|---|---|
| **4 敌种全覆盖** | ci_li（地刺，3 处）、du_fu（漂浮，2 处）、chong_feng（冲锋，2 处，警示红）、shi_pao（石炮，2 处） | `entities[]` 与 1-1 同 JSON 形态，零新 type |
| **金币 coin** | 9 枚，分布于地面与高位路线（含 beat 平台上方赏金） | 经济链路 S04-3/S04-4 复用 |
| **种子 seed** | 2 颗（`seed_01` 前段、`seed_02` 后段），触发 `ON_SEED_COLLECTED` | 蜕变内核曝光，局内累积留专项 Story |
| **检查点 checkpoint** | 2 个（mid `x=960`、gauntlet 前 `x=1248`），更新 respawnPoint + `ON_CHECKPOINT` | 双检查点证明重生语义在更长关卡仍稳 |
| **凯旋之门 goal** | `type:"triumph_gate"`，`x=1472,y=160,w=32,h=64`（IP 安全终点，替代旗杆） | 与 1-1 完全一致 |
| **节拍平台 beatPlatforms** | 1 段 `bp_1_2`（tx19-21,ty5，initial ghost），由 `beat.tracks[].target` 引用 | 周期性 solid/ghost 切换；更紧 pattern 验证相位可定制 |
| **oneway 单向台** | 2 组（tx12-14,ty5；tx33-35,ty6），kind=`oneway` | 纵向跳跃复用 |
| **悬浮 solid 台** | 1 组（tx26-27,ty4），kind=`solid` | 高位路线落脚点复用 |
| **地面 + 边界墙约定** | 地面 ty7-8 全宽连续；左 tx0 / 右 tx47 两列 ty0-8 为墙 | 与 1-1 同网格约定，坐标可直接编译 |

**结论**：1-2 不引入任何新实体/新 tile kind，全部为 1-1 同款数据的「不同排列与密度」。若 1-2 能被 loader 原样加载、渲染、通关，即证明「关卡内容流水线」已可参数化复用，具备批量产关能力。

## 5. parTimeMs 建议

- **建议值：`84000`（84 秒）**，并标注为「建议基准值，待 QA 实跑调校」。
- 理由：1-1 占位 60000 对应 width 40（1280px）；1-2 width 48（+20% 路程）且敌人密度 ×2、含更紧节拍段与双检查点缓冲，按「路程 + 战斗/时机损耗 ≈ +40%」估得 ~84000。若主理人倾向保守，可先沿用占位 `60000` 并标注，待 playtest 后回填真实值——此决策点列于第 7 节。

## 6. 节拍段（Beat）设计说明

- `beat.enabled=true`，`bpm=120`，`grid=8`（与 1-1 同引擎参数，验证参数化）。
- 1 条 track：`target:"bp_1_2"`，`pattern:"GSGSGSGSGSGSGSGS"`（16 字符，G=ghost/S=solid 交替）。
- **语义假设（需工程核对，见决策点 D4）**：按本 schema，`pattern` 每字符对应 1 beat；bpm 120 → 1 beat = 500ms。故本 pattern = **500ms 实 / 500ms 虚** 循环（相对 1-1 的 `SSSSSSSSGGGGGGGG`=4s/4s 明显更紧）。
- ⚠️ 注意：1-1 的 `metadata.parTimeMs` 注释与 JSON 实际 pattern 存在口径出入（文档称「实500ms/虚500ms」，JSON 实为 16 字符=8s/8s）。我已按「1 字符=1 beat=500ms」在 1-2 取更紧 pattern，并请主理人/工程确认引擎真实 tick 语义后再定稿。若引擎实为「每 pattern 字符=1 拍且整段=1 周期循环」，则本 pattern 正好达成 500ms 交替，符合预期。
