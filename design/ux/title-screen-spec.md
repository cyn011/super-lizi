## 4. ⚠️ 文字渲染关键技术约束（v2 核心修复）

### 4.1 禁止 `setResolution(4)` —— 根因说明

**问题现象**：v1 实现在所有 Phaser Text 对象上调用了 `.setResolution(4)`，导致：
- 逻辑字号 32px 的文本以 **4× 分辨率栅格化** = 实际渲染为 **128px 等效尺寸**；
- 24px 的副标题渲染为 **96px 等效**；
- 文字互相重叠、溢出屏幕、完全不可读。

**技术原理**：Phaser 的 `setResolution(r)` 控制 Canvas 2D 文本栅格化的 DPI 倍率。设 r=4 意味着在 4× 密度画布上栅格文字后再缩放回逻辑尺寸——对矢量系统字体而言，这直接让视觉尺寸膨胀约 4 倍（因为栅格化后的位图被当作普通纹理显示）。

**v2 规则**：
1. **严禁**在任何标题屏 Text 对象上调用 `.setResolution(4)` 或任何 >2 的 resolution 值。
2. 使用**正确的逻辑字号**（见下表），让游戏缩放管线（`pixelArt:true` + FIT/整数缩放）统一处理上采样。
3. 如需提升文字锐度，可选方案（按推荐排序）：
   - **方案 A（首选）**：不做特殊处理，依赖 `pixelArt:true` 的 nearest 上采样。系统字体在 512×288 逻辑缓冲中以正常字号栅格化后整数倍放大，结果清晰可用。
   - **方案 B**：使用**适度的** `setResolution(1.5)` 或 `setResolution(2)` —— 仅在整数缩放模式下测试确认不溢出后方可采用。**必须逐字号验证**。
   - **方案 C（最清晰但高成本）**：DOM HTML 叠层覆盖（设备分辨率原生渲染）。**本期不做**，留后续增强。

## 5. 微信胶囊安全区

- **胶囊位置**：微信客户端在 canvas **右上角**叠加胶囊菜单按钮（约 87×32 CSS px，含圆角）。横屏下覆盖 canvas 右上区域，会遮挡其下内容。
- **预留区（强制）**：`capsule zone = (420,0)–(512,44)`（宽 92 × 高 44 逻辑 px）。
- **规则**：
  - 任何**可见内容或交互热区**不得进入 capsule zone。
  - 全局 `safe frame` 内缩 12px（顶/左/右/底），与 capsule zone 取并集约束。
  - **Mali 特殊处理**：栗宝主体（身体/面部/眼睛）必须在 x ≤ 418；头顶嫩芽和手中花朵作为**纯装饰性延伸**可轻微越界至 x ~424（非交互、遮挡可接受）。
  - **城堡剪影**：处于 depth 3.5（远景底层），若塔尖被胶囊遮挡不影响体验；否则左移至 x<420。
  - `BUILD_LABEL` 在**右下** `(506,282)`，远离胶囊——保留。
  - 标题/按钮/标语均位于 x<420 或 y>44，满足约束。
- **真机校准**：不同机型胶囊尺寸/边距略有差异；QA 在真机横屏核对 capsule zone 无遮挡，必要时整体上调 safe frame 至 16px。

## 6. 交互规格

**主 CTA「▶ 开始冒险」→ 进入 PLAYING：**
- 触发：`pointerdown` / 点击 / 键盘 `ENTER` / 键盘 `SPACE` → 调 `startGame()`。

- 防重复触发：沿用 `started` 布尔锁 + `built` 幂等锁。

**继续行（continue）：**
- 仅当 `SaveData.lastUnlockedLevel > 1`（存在进度）时显示并可选；点击 → 进对应关。
- **无存档时**：隐藏（最干净）。
- 位置：底部居中 (256,262)，极小 9px 字，**不干扰主封面**。

**按钮状态机：**

| 状态 | 视觉 | 时长/反馈 |
|---|---|---|
| idle | 暖橙填充 + OUTLINE 描边 + 外发光呼吸 | 常态；呼吸脉冲见 §7 |
| hover（桌面 pointerover） | 放大 1.06 + 发光增强；呼吸暂停 | 即时（<16ms） |
| press（pointerdown） | 缩小 0.96 + 填充转深橙 | 即时反馈 <120ms，松手回 idle |
| disabled（仅继续行无存档） | 不适用（直接隐藏） | — |

- 热区 ≥ 48×48 逻辑 px：主按钮视觉 180×44，交互命中区扩展至整按钮容器（满足）。
- 桌面 hover 仅 Web（`env==='web'` 时挂 `pointerover/out`）；微信无 hover，以 press 反馈替代。

## 8. 响应式 / 缩放规则

- **唯一真相源**：512×288 逻辑设计空间；所有坐标取自此文档。
- **Web（推荐整数缩放，消除模糊）：**
  - 首选：手动整数缩放——`k = max(1, floor(min(displayW/512, displayH/288)))`，`Scale.NONE` + 画布尺寸 `512k × 288k` 居中，四周 letterbox。保证 **整数倍** nearest 上采样 → 矢量图形与系统字体均硬边清晰。
  - 回退：`Scale.FIT` + `pixelArt:true` + `roundPixels:true`。
- **微信小游戏：**
  - canvas 由微信客户端缩放至设备；沿用同一 `pixelArt:true` 保证 nearest 上采样。
  - 胶囊由微信叠加在 canvas 右上，**capsule zone（§5）** 保内容不碰撞。
  - 所有坐标**硬编码逻辑值**，不读 `this.scale`。
- **文字清晰度（v2 核心）**：
  - ❌ **禁止** `setResolution(4)` 或任何 >2 的 resolution 值（见 §4.1 详细说明）。
  - ✅ 使用标准逻辑字号（§4.2 表格），依赖缩放管线统一处理。
  - ✅ 如需锐度增强，最大尝试 `setResolution(1.5)` 并逐元素验证不溢出。

## 附录 A：已知风险 / 取舍

- **木牌 Graphics 绘制复杂度**：木质徽章 + 叶/花装饰全用 Phaser Graphics 原语（fillRoundedRect/fillEllipse/fillCircle 组合）可实现，但代码量较大。取舍：MVP 先用**简化版**（圆角矩形木纹色衬条 + 2–3 片叶子椭圆），后续迭代增加细节；或采用 §9.2 的替代方案（圆角木纹矩形衬条）。
- **Mali 右侧空间受限**：胶囊区占去右上 92×44，Mali 只能在 x370–418 范围内放置（宽 48px）。若 48px 太窄：①接受瘦高型栗宝（压缩水平比例）；②让栗宝稍微转向（3/4 侧面，减少水平占地）；③允许更多装饰性部位（花/芽）越界。
- **新增装饰元素的性能预算**：雪山、城堡、大树、蘑菇、路牌合计约 10–15 个新增 Graphics 对象（静态）。ADR-004 的 draw call 预算内应可容纳（当前场景约 25 个 draw call，新增后约 40 个，仍在安全范围）。若超预算则优先砍城堡和蘑菇。
- **文字清晰度 vs 整数缩放**：放弃 `setResolution(4)` 后，FIT 模式（非整数）下系统字体可能有轻微软边。取舍：推荐 Web 端优先整数缩放模式（已在 v1 中规划）；微信端 `pixelArt:true` 的 nearest 上采样对小字号基本够用。
- **参考图 vs 实现差距预期**：参考图为高分辨率美术概念图（可能来自专业美术工具），本 spec 落地为 Phaser Graphics 原语实时绘制。无法达到参考图的精细度（木纹质感、光影渐变、角色表情丰富度等），但**布局/构图/比例/氛围**应高度一致。美术品质差距由后续资源替换阶段弥补。
